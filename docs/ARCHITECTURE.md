# OntoCare 架构说明

## 架构目标

把售后客服拆成可验证的数据理解、对象关联、规则判断和安全响应步骤。设计优先保证证据来源清楚、状态可追踪和高风险写操作有明确边界，而不是让模型直接决定所有业务事实。

## 主要组件

- `static/index.html`：对话窗口与右侧过程面板。
- `app.py`：Flask 路由、请求编排、模型调用、模拟数据查询、决策和响应组装。
- `dialogue.py`：有限会话历史、槽位显示、阶段计算、结束语与脱敏辅助逻辑。
- `workflow.py`：工作项、工具步骤轨迹和未提交的人工审核草稿。
- `ontology.py` / `data/ontology.json`：本体对象/关系与动作合法性校验。
- `data/*.json`：合成产品、订单、经销商、知识和策略资料。

## 状态与证据模型

案件状态和外部事实分开管理。模型从自然语言提出候选；用户陈述以 claim 保存；本地订单/目录命中带测试来源；规则运行得到决策状态。冲突或缺失时保留 UNKNOWN、CONFLICTED 或待核验状态，不以自由文本强行覆盖权威字段。案件阶段由状态函数计算，不单独让模型自由命名。

## 安全动作空间

规则输出允许与禁止动作，并携带原因和规则版本。系统没有真实订单写工具；退款/换货/补发相关诉求只转成待人工审核草稿，状态是 `DRAFT_NOT_SUBMITTED`。页面中的工具轨迹代表本地函数或模拟数据读取，不代表真实外部系统执行。

## 多轮工作方式

同一会话保存短期历史和结构化槽位。连续追问会将当前产品、故障、已尝试步骤和诉求与本轮输入合并理解。结束语识别用于结束当前案件；“没有订单号”属于槽位缺失回答。状态保存在单进程内存，因此服务重启、扩容和多 worker 需要后续持久化设计。

## 失败边界

未配置模型或调用失败时应显示失败状态；不能回放固定答案。订单查无不能推导过保；型号歧义时应澄清；图片能力不能从上传接口存在推断为已验证识别；无身份/归属核验时不能声称访客拥有订单。
